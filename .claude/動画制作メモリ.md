### 書き方

- **番号を振って、上から順にやれば終わる形にする**
- **押す番号・打つ文字をそのまま書く。**「メニューから選ぶ」では足りない
- **1回だけでいいこと**（pip install など）と、**毎回やること**を分ける
- **やらなくていいことは「やらなくていい」と書く。** 前に言った手順が
  要らなくなったら、そう言わないと本人はやり続ける
- 待ち時間の目安を書く（11分なのか1時間なのか）
- **最後に「こちらに貼るもの」を書く。** 採点.txt なのか一覧.txt なのか

### いまのメニュー（はじめる.bat）


## 「ずれ」の本当の正体（2026-10-06・ここで決着）

本人は **5回**「まだずれています」と言い、こちらは毎回「直した」と言って出した。
最後は「いい加減完璧に直してください」。原因は2つあり、**両方こちら側**。

### ① 測り方が壊れていた（これに気づくのが先だった）

`ずれ検査.py` は、出来た割り当て表と正解を **本文で突き合わせていた。**
作った材料には同じ文字列のかたまりがあるので、
「本文が合わない」が1枚出たとたん**そこから先が1つずつ食いちがい**、
**7.25秒という偽のずれ**が出ていた。しかも合格の線は
「平均と割合だけ。最大は見ない」にしてあったので、
**7.25秒ずれていても ○ を出していた。**

> 「材料のクセだから最大は見ない」は、検査が通るように線を動かしただけ。

いまは、かたまり1つ1つに**重ならない背番号**（ふつうのカタカナ3文字）を
付けて一対一で突き合わせる。一対一にならなければ、ずれではなく
**検査の失敗**として落とす。合格の線に**最大を入れた**。

### ② 「数が合うこと」を「位置が合っている証拠」にしていた

`place_in_chunk`（かたまりの中で文の切れ目を置くところ）は、
無音を長さで絞っていって **ちょうど k-1 個** になったら、
**位置をまったく見ずに**それを文の切れ目と決めていた（「推測ゼロ」と称して）。

実測した例（段落24・9かたまり）

| | 1つめ | 2つめ |
|---|---|---|
| 本当の文の切れ目 | 418.45 | 427.90 |
| 文字数で割った目安 | 418.07 | 426.88 |
| 「ちょうど2個」で確定 | **415.14** | **418.33**（9.6秒 早い） |

0.32秒以上の間がたまたま2つあっただけで、1つは「、」の息継ぎだった。
しかもここで決まった切れ目は**錨として固定される**ので、あとで誰も直せない。
その段落の字幕・絵・声がまるごとずれ、次の段落の頭で戻る。
本人がずっと言っていた **「その区間だけずれる。ほかは問題ない」** はこれ。

### 直し方 ─ 当てずっぽうをやめて、1行ずつの音声で**実際に測る**

いちばん効いたのはこれ。
文の長さを「文字数 ÷ 一定の速さ」で見積もるのをやめ、
**1行ずつの音声（output/0NN.wav）の中の「間」を数えて、本当の長さを測る。**
merged.wav は つなぐときに前後を削っているが、1行ずつの音声は削る前なので、
その中の「間」は台本の「、」「。」とそのまま対応する。
声の区間の数が「、」の数と合ったときだけ使い、合わなければ文字数で割る道に落ちる。

**ただし「数が合ったこと」は位置の証拠に使わない。**（②の二の舞を避ける）
使うのは**長さの割合だけ**で、位置はこのあと本物の間に寄せるときに決まる。

実測（乱数8通り × 区切り330枚）

| | 最大 | 平均 | 0.3秒超 |
|---|---|---|---|
| 直す前 | **8.66秒** | 0.37 | 7% |
| place_in_chunk を直して | 1.88秒 | 0.16 | 2% |
| 「、」の切れ目に罰を入れて | 1.68秒 | 0.16 | 2% |
| **1行ずつの音声で実測して** | **0.49秒** | **0.16** | **0〜1%** |

残る 0.24秒 は LEAD（字幕を声の 0.12秒前に出す）の設計ぶん。

### 予備の道も必ず測る

本物の読み上げが「、」で必ず息を継ぐとはかぎらない。
数が合わなければ文字数で割る道に落ちるので、
**`ずれ検査.py` は「実測あり」と「実測なし」の両方を測る。**
片方しか測らないと、本人の画面でだけずれる、がまた起きる。

### 「数字が1桁も動かない」は、その工程を通っていない印

測った長さを入れても結果が変わらないことが**4回続いた**。
そのたびに別の原因を疑ったが、実際は**毎回ちがう場所で捨てられていた**。

 ① 数がぴったり合うときだけ使う（→順番を保つ対応づけに。54/54 になった）
 ② koma_awase が、測った見当を捨てて文字数から作り直していた
 ③ refine_cues が、**その前に**もう文字数で割っていた
 ④ 引き出しを「前から使い切る」形にして、外側の呼び出しが使い切っていた
 ⑤ 「、」が2つ以上の文しか記録せず、1つ欠けると字幕まるごと落ちた

- **8分以上にする。** YouTubeのミッドロール（途中広告）は8分以上の動画だけ。
  かつては10分だったが2020年に8分へ短縮された。ねらいは8分30秒〜8分50秒。
- **口調は「第6回 ヒトガミの正体」が見本。** 本人が書いた原稿に合わせた形。
  ・冒頭は事実の言い切り。「老デウスの歩んできた人生が、壮絶すぎた。」
  ・次に「どうもこんにちは、かさです。」（あいさつは読み辞書で変換しない）
  ・「ということで今回の動画は、〜について考察していきたいと思います。」
  ・一人称で考えながら話す。「〜というわけです」「〜なんだとか」「〜かと思います」
  ・読者の疑問を先回りして口語で置く。「なら先に殺せばいいやん、となる方も」
  ・章の予告は「そして二つ目の助言は」「と、〜のことはここまでとして。」で自然にやる
  **これまでの硬い解説調ではなく、この考察調に全部そろえる。**
- 組み立て：
  1. 挨拶（「無職転生、〜」）＋ **最初の80字にその回いちばん強い事実**
     （挨拶だけだと掴みが目次になる。事実を同居させる）
  2. 今回話す内容の概要
  3. どう進めるかの予告（章立て）
  4. ネタバレの断り
  5. **「それでは早速みていきます」** で本編へ
  6. 章ごとに「次は〜の話です」と予告
- 導入は180字（30秒）まで。中盤に引き留めを1つ。固有名詞は20種類以上。
- `kaku.py --check` で健康診断。`kaku.py --yomi` でカタカナ変換（実測93.8%）。
- 「第N話」→「第Nワ」は**正しい**（だいじゅういちわ と読ませるため）。
  「では」はそのまま（VOICEPEAKが正しく読む）。直すのは `読み辞書.txt`。

## 3. 字幕の切り方（何度も変えたので、順位ごと覚える）

**いまの既定は「「、」ごとに切る」（元の動き）に戻してある。**
本人から「字幕と音声がずれた」と言われて戻した。ただし下の検算のとおり、
**分割の設定で字幕がずれることはない。** 戻したのは指示だから。
細かくしたいときは `--kuten-moji 20 --kuten-tsunagi 5 --kuten-min 1.5`。

**優先順位：「。」で切る ＞ 短すぎない ＞ 長すぎない**
上から譲らない。これを決めていないと、条件が増えるたびに壊れる。

1. `。` `！` `？` は**必ず**切る。**ここは絶対。またいで結合しない。**
2. `、` は合計 **20文字**を超えないように切る（`--kuten-moji 20`）
3. **5文字以下、または1.5秒未満**は**後ろ**にくっつける
   （`--kuten-tsunagi 5` / `--kuten-min 1.5`）。「前」ではない（語順が変わる）
4. `、` が1つも無くて長い文は**切らない**。切る場所が無いので、しょうがない。
5. ②と③がぶつかったら③を上にする。結果20字超過が2割ほど出るが、承知の上。

3380字の台本で **209か所・1枚2.5秒**。数字を変えたときの目安：
18字/1.1秒→225枚、20字/1.5秒→209枚、24字/1.5秒→197枚。

## 4. 画像を文章に合わせる

- **`画像カタログ.txt` には見た目のタグだけ入れる**（髪色・年齢・服・持ち物）。
  人物名は `人物ルール.txt` で**読み込むときに**決める。
  こうしておけば、ルールを1行直すだけで1万枚の判定がやり直せる。**再解析しない。**
- `@@話数` は `#指定` の探す範囲。**その中に無ければカンマの次の候補に譲る。**
  全部外れたときだけ他の話数へ広げる。これを忘れると黙って他の期から拾ってくる。
  （話数の種類が11 → 4 に減った。いちばん効いた直し）
- **当たった規則のうち「いちばん長いキー」を使う。** 先に書いた行ではない。
  短いキーが後ろの文まで拾う（「この時」が「この時点で…」を拾った）。
- 同じ絵は直前12か所に出たら避ける（`AVOID_WINDOW`）。
- 同じ文の続きでも絵は次へ進める。前と同じ番号にすると句読点で割った意味が無い。
- セリフの人名と絵の人物が**別人**のときだけ選び直す。誰も写っていない絵はそのまま。
  選び直しは**必ず対象話数の中から**探す。
- **老デウスは年をとったルーデウス本人。** どちらの絵でも間違いではない。

### 設定ファイルに書き足すときは、改行を二重にしない（2026-10-06）

`人物ルール.txt` は CRLF。そこへ CRLF の文字列を足して `\r\r\n` になった。
読む側は `.replace("\r\n","\n")` だけなので、行のうしろに `\r` が残る。
`strip()` でたまたま消えていたが、タブで割る所に来れば黙って壊れる。
**`パック検査.py` が video フォルダの .txt ぜんぶを見るようにした**（仕上げ.py の ⑱）。

このとき、最初は `sync_py.py` の表（.py だけ）を見ていて、
**1つも調べない検査**になっていた。見た数を数えて、少なすぎたら落とすようにした。

### 誰の絵かは、**その1行だけでは決まらない**（2026-10-06・本人の理由から）

### 手で選んだ絵は、機械の判定より上（5か所そろえる）

画像プランに**ファイル名を直接**書いた絵は、
① 対象話数の外でも使う ② `使用不可` でも使う ③ 人ちがいの選び直しをしない
④ 採点でも責めない（**絵の番号で書いたものも、差し替え.txt のぶんも**）

2回目以降は自動に回したいので、うしろに `#指定` を並べる。

## 5. 見ずに直す仕組み（採点）

## 14. 演出（切り替え効果と効果音）

`演出.txt` で設定する。**台本も音声も作り直さずに、演出だけ変えられる。**

    切り替え	0.25     ← 前の絵から溶かす秒数。0 で効果なし
    効果音	なし      ← なし / シュッ / ポン / カッ / 自分の.wav
    効果音の音量	0.4

### 尺を1フレームも狂わせない作り（ここが肝心）

`xfade` は**使わない。** 重ねたぶん全体が縮み、音とずれるため。
209か所×0.3秒なら62秒も短くなってしまう。

代わりに、**断片の頭に前の絵を重ねて、それを透明にしていく。**

    [1:v]format=yuva420p,fade=t=out:st=0:d=D:alpha=1[f];
    [0:v][f]overlay,format=yuv420p[v]

断片の長さは `-frames:v N` のままなので、**フレーム数が変わらない。**
実測：演出なし360フレーム/12.00秒 → 演出あり360フレーム/12.00秒。同じ。

効果音も同じ考え方。`adelay` を何百個も並べるとグラフが大きすぎるので、
**無音のバイト列に貼りつけて1本のwavを作る**（209か所で0.67秒）。
混ぜるときは `amix=inputs=2:duration=first:normalize=0`。
**normalize=0 を忘れると声の音量が下がる。** duration=first で長さは声のまま。
実測：声も混ぜたあとも 23,064,300サンプルで同じ。

### 区切りの種類ごとに、音とエフェクトを変える（本人の指定）

    区切り	。	カメラ.mp3	暗転	0.12
    区切り	、	はさみ.mp3	はさみ	0.16
    区切り	章	カードをめくる.mp3	ページめくり	0.40

種類は強い順に 章 ＞ 。 ＞ 、。前のセリフが「。」で終わっていれば「。」扱い。
**効果音3つは本人からもらった実物**（`効果音/` に同梱済み）。

**音は「立ち上がり」を切り替わりに合わせる。** ファイルの頭ではない。
カメラは0.05秒、はさみは0.05秒、カードは0.10〜0.25秒あとに鳴るので、
そのぶん前に置かないと、音が遅れて聞こえる。`se_wav_ready` が自動で測る。

エフェクトの作り（どれも尺を変えない）:

    暗転        [0:v]fade=t=in:st=0:d=D
    はさみ      前の絵を重ね、overlay x='-(w*t/D)' で左へ抜く
    ページめくり 前の絵を下に、新しい絵を overlay x='W-(W*t/D)' で右から入れる
    溶ける      前の絵を重ね、alpha を落とす

### BGM（2026-09-29 追加）

**採用した曲だけ掲示板に埋め込む。** `build.py` が
`scratchpad/video/BGM/*` を base64 で `<script data-bgm>` にする。
ふおんなきり.mp3（1.16MB）を入れて掲示板は 2.28MB → 3.70MB。
**候補を全部は入れられない**（20本なら32MBで、上限16MBを超える）。
候補は数字で測って（長さ・LUFS・前後の無音・いちばん静かな所）本人に選んでもらい、
選ばれたものだけ入れる。作業フォルダ側の `BGM` フォルダは `Prepare` が必ず作る。

`演出.txt` のいちばん下：

```
BGM	ふおんなきり.mp3
BGMの音量	0.10
BGMのフェード	3
BGM控えめ	はい
```

- **足りなければくり返す。長ければ切る（`-t`）。**
  くり返しは `-stream_loop` だけでは**だめ**。実際の曲（ふおんなきり.mp3）で、
  頭に0.5秒・終わりに2秒の無音があり、1周ごとに**-44dB の穴**があいた。
  二段構えにすること：
  1. `bgm_mugon_kezuru` … 20msごとの山の高さを見て、いちばん大きい所の
     2%未満を無音とみなして前後を削る。両端に15msのフェード（プツッ消し）。
  2. `bgm_tsunagu` … 終わりの2秒と次の頭の2秒を、四分の一円の形で
     重ねて入れかえる（等パワーのクロスフェード）。
     23,064,300サンプルを触るので **`array('h')` を使う**。
     ふつうの list だと int が1個28バイトで 600MB を超える。
  結果、つなぎ目は -19.1dB（前後 -14.8 / -17.5）。穴がなくなった。
- **頭と終わりは afade。** 終わりは「動画と声の短い方」に合わせて終わる。
- **BGM控えめ＝ダッキング**（`sidechaincompress`、声を鍵にする）。
  実測で **0.35倍**まで下がる。使えない ffmpeg では自動であきらめて、
  音量そのままで入れる（ずれなどの害は出ない）。
- **`sidechaincompress` は終わりを 0.48秒ほど削る。**
  `apad` と `-t` で元の長さに戻すこと。戻さないと BGM だけ早く終わる。
  長さの確認は **ffprobe ではなく `wave` モジュールで数える**
  （同梱の ffprobe は当てにならず、11.52秒と嘘をついた）。

**検算（毎回これを通す）**
1. 長さが動画ちょうど（529200サンプル＝12.000000秒）
2. 5秒の曲が12秒までくり返されている
3. 頭0.3秒と終わり0.3秒が、まんなかの 0.06倍
4. ダッキングで短くならない
5. **声＋効果音＋BGM を混ぜたものから、効果音とBGMを引くと、声と完全に一致（差 0）**

`amix` は **`normalize=0`** と **`duration=first`**。本数が増えても同じ。

## 14.6 絵をゆっくり横に動かす（2026-10-03・本人の指定）

> **これは全動画の決めごと。言われなくても毎回付ける（2026-10-04・本人の指定）**
>
> 本人の言葉：「**画像を動かすのはいい感じなので、これを以降の動画作成すべてに
> 適用できるようにメモリに保存してください**」。
>
> つまり 14.6／14.61／14.62 の3つは、新しい動画でも**既定で入っている状態**にする。
> 置き場所は `見た目.txt`（全動画共通）なので、**動画ごとに書き足すものは何も無い。**
> 新しい台本を足したときに確かめるのは次の3つだけ：
>
> 1. `見た目.txt` に `画像を動かす はい` が残っているか（既定値も「はい」）
> 2. パックに `見た目.txt` が配られているか（`pushKyotsu()`・仕上げ.py ⑤）
> 3. 章カードは動かさない（左右で絵と字を分けているので、動くと崩れる）
>
> **止めたいときだけ** `見た目.txt` の `画像を動かす` を `いいえ` にする。
> 速さ・拡大・向きの決め方を変えるときも、直すのは `見た目.txt` の1行だけで、
> `make_slideshow.py` には触らない。

本人の指定：「各セリフの画像すべてで、画像が右から左へゆっくり移動する動きを
つけたい。画像を今の10%程度拡大し、左寄せで表示しておき、一定のスピードで
流れていく。**いちばん長い尺でも見切れない速さを計算し、全ての画像で同じ
スピードに**」。

### 速さの決め方

```
余り        = 画面の幅 ×(拡大 − 1)        1920 × 0.10 = 192px
1秒あたり   = 余り ÷ いちばん長く映る絵の尺   192 ÷ 4.07 = 毎秒 47.2px
```

**いちばん長い絵でちょうど右端まで行き、それより短い絵は途中で止まる。**
どの絵も端が切れない。短い絵ほど動く量が少ないだけで、速さは同じなので、
見ていて調子が乱れない。

実測（1920×1080・1.10倍・いちばん長い 4.07秒）:

| 尺 | 切り出し位置 | 動いた量 | 計算値 |
|---|---|---|---|
| 4.07秒 | 0 → 189px | 189px | 192px |
| 2.00秒 | 0 → 92px | 92px | 94px |

**192px を一度も超えない＝端が切れない。**
（最後のコマは1/30秒手前なので、計算値よりわずかに小さいのが正しい）

### 作り

- `normalize` で**あらかじめ 2112×1188 にそろえる**（毎回拡大しない）
- 断片ごとに `crop=1920:1080:x='min(192,47.2*t)':y=(ih-1080)/2`
  crop の x に `t` を入れると1コマずつ計算し直す。`min` で右端を越えない
- 縦は真ん中で固定（上下には動かさない）
- **章カードは動かさない。** 左右で絵と文字を分けているので、動くと崩れる
- エフェクト付きの断片では `[0:v]`→`[c0]`、`[1:v]`→`[c1]` に差し替えて、
  切り出しを通してからエフェクトをかける

### 速さは「使い切る速さ」の 0.75倍（2026-10-04・本人の指定）

ちょうど右端まで使い切る速さは、本人が見て**少し速かった**。
「その 0.75倍に全て変更して」とのことで、倍率を設定にした。

```
速さ = 余り ÷ いちばん長い尺 × 動きの速さ
     = 192 ÷ 4.07 × 0.75
     = 毎秒 35.4px
```

実測（1.10倍・いちばん長い 4.07秒・0.75倍）:

| 尺 | 動いた量 | 余り192pxのうち |
|---|---|---|
| 4.07秒 | 141px | 73% |
| 2.00秒 | 70px | 36% |

**いちばん長い絵でも端まで 48px 残る。** 下げるぶんには切れる心配が増えない。

### 設定（見た目.txt）

```
画像を動かす	はい
画像の拡大	1.10
動きの速さ	0.75      ← 1.00 で「いちばん長い絵が右端ぴったり」
```

- **拡大**を上げると動かせる幅が増えるが、絵は粗くなる
- **動きの速さ**は 1.00 で頭打ちにしてある。
  超えるといちばん長い絵で端が切れるため

## 14.61 動きの向きは4つからバラバラに（2026-10-04・本人の指定）

本人の指摘：「今は右から左へ動いていますが、**すべて同じ方向に動いており、
すごくくどい**。右から左、左から右、上から下、下から上の四つのパターンを
各画像でランダムに」。

### 4方向を同じ速さ・同じ距離にそろえる

1.10倍にすると、余りは **横192px・縦108px とちがう。**
向きごとに距離を変えると、縦のときだけ速く見えてしまう。

```
動く距離 = min(横の余り, 縦の余り)    = 108px
速さ     = 距離 ÷ いちばん長い尺 × 0.75 = 毎秒 19.9px
```

**小さいほうにそろえる。** 距離が縮むので、本人の「もう少し遅く」も同時に満たす
（毎秒 35.4 → 19.9px）。

## 14.63 行の境目は、一律倍率ではなく本物の無音に合わせる（2026-10-04）

本人の指摘：「字幕と音声がずれています」「**ずれの傾向は、最初の冒頭から、
ヒトガミの目的の章が始まるまでの間**です」。

### 症状の形がそのまま答えだった

**前半だけずれて、後半は合っている。** これは「全体が速い／遅い」ではない。
合計は合っているのに途中が合わない＝**途中の配り方**がおかしい。

### 原因：縮みは行の長さに比例しない

ログにこう出ていた。

```
1行ずつの音声 54個 の実測 540.81秒 → merged.wav 534.44秒 (0.9882倍)
```

つなぐときに行の前後の無音を削るので、merged.wav は 6.4秒ぶん縮む。
ところが**この縮みは行の長さに比例しない。**
後ろに長い間がある行はたくさん削られ、間の無い行はほとんど削られない。

それを `t += durs[i] * 0.9882` と**一律の倍率**で配っていた。

- 平均より多く削られた行のあとは、字幕が**遅れる**
- 平均より少ない行のあとは、字幕が**早まる**
- そして合計は必ず合うので、**最後だけぴったり合い、途中がずれる**

ずれは前半で積み上がり、後半で返していく。本人の「冒頭から
ヒトガミの目的の章まで」は、積み上がっていた区間そのもの。

### 直し方：無音のまん中へ寄せる（`kugiri_awase`）

行の境目は、merged.wav の中では**必ず無音の中にある**（そこを削ったのだから）。
目安の近く（±1.5秒）に無音があれば、その**まん中**へ寄せる。無ければ目安のまま。

```python
for k in range(1, n):
    nokori_honto = total - t                      # 残っている本物の時間
    nokori_yomi  = sum(durs[k-1:])                # 残っている読み上げ時間
    mezasu = t + durs[k-1] * (nokori_honto / nokori_yomi)
    …いちばん近い無音のまん中へ（±1.5秒以内・t より後ろだけ）
```

### 肝心なのは「合わせるたびに測り直す」こと

最初は窓を固定して1回ずつ寄せただけで、**4か所のうち2か所しか直らなかった。**
一度ずれたまま次の目安を出すと、ずれが積み上がって窓から外れ、
そこから先が全部合わなくなる。

**寄せた位置から残りを測り直す**（上の `nokori_honto / nokori_yomi`）と、
ずれを次へ持ち越さない。

```
一律倍率のいちばん大きいずれ : 2.28秒
合わせ直したあと             : 0.00秒
```

### 気をつけたこと

- 順番が入れ替わらないようにだけ見る（`t + 0.05` より後ろしか選ばない）
- 端（0 と total）はぴったりのまま
- 無音が無い／多すぎる／1行／2行 でも落ちないことを確かめた
- 0.15秒以上寄せたときは、画面と `確認用/一覧.txt` に
  「境目を無音に合わせ直しました(最大 ○秒ぶん)」と出す

## 21. 掲示板を2枚に分けた（2026-10-07・本人の指定）

```

```
